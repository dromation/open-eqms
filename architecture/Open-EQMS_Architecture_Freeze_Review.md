# Open-EQMS Architecture Freeze Review

Status: Historical / Explanatory / Non-normative

This document records the final architecture review prompt before implementation. It is historical context for Architecture Baseline v1.0 and is not the authoritative implementation reference.

## Role

You are acting as the Chief Systems Architect of the Open-EQMS project.

This is the final architecture review before implementation begins.

The objective is not to redesign the platform.

The objective is to verify that the architecture is internally consistent, deterministic, maintainable, lightweight, and suitable for long-term industrial use.

This review should result in Architecture Baseline v1.0.

Do not introduce unnecessary new concepts.

Simplify wherever possible.

Preserve the philosophy.

## Project Vision

Open-EQMS is not another ERP.

Open-EQMS is not another QMS.

Open-EQMS is not another document management system.

Open-EQMS is intended to become a lightweight deterministic Business Runtime Platform.

Think of it as a Business Runtime Engine that executes configurable enterprise systems.

The inspiration comes from classic game engines. Not because of games. Because they successfully separated:

- Runtime.
- Content.

The Runtime remains stable.

Content evolves independently.

## Fundamental Principles

- The Runtime contains only universal concepts.
- The Runtime must never contain business methods.
- Business methods belong entirely inside Content Packages.
- The Runtime should remain usable for decades.
- Business packages may evolve independently.
- Optional functionality must never increase the minimum Runtime footprint.
- The Runtime must remain deterministic.
- Everything visible to users must be localizable.
- Offline operation is mandatory.
- Open-source sustainability is a primary design goal.

## Runtime Responsibilities

Current Runtime proposal:

- Object Runtime.
- Event Engine.
- Rule Engine.
- Process Engine.
- Statistics Engine.
- KPI Engine.
- Query Engine.
- Transaction Engine.
- Package Loader.
- Native GUI Renderer.
- Synchronization Engine.
- Security.

The previous architecture intentionally removed:

- Resource Runtime.
- State Engine.

Resources are Object types.

State transitions belong to the Process Engine.

Please verify this simplification.

## Object Model

Everything inside the Runtime is ultimately represented as Objects.

Examples:

- Employee.
- Machine.
- Supplier.
- Customer.
- Material.
- Product.
- BOM.
- Document.
- Measurement.
- Task.
- Complaint.
- Audit.

Objects are generic.

Business semantics come entirely from packages.

Please verify this philosophy.

## Event Philosophy

The Runtime is event-driven.

Events represent facts.

Facts are never deleted.

Rules evaluate facts.

Processes react to rule results.

Current state is updated only through validated transactions.

The architecture separates:

- Current Object State.
- Business Event Log.
- Rule Evaluation Log.
- Transaction / Audit Log.

Please verify whether this separation is sufficient and internally consistent.

## Rule Philosophy

Business Rules remain deterministic.

Packages should be approximately 90% declarative.

The Rule DSL should remain intentionally small.

The Rule DSL must not become a second programming language.

The Rule DSL must call the Query Engine for filtering and aggregation instead of implementing duplicate query syntax.

Runtime must enforce:

- Maximum rule depth.
- Maximum iterations.
- Maximum chain length.
- Maximum execution time.
- Cycle detection.
- Recursion detection.
- Maximum generated events.
- Maximum generated actions.

Please verify this architecture.

## Query Engine

The Query Engine is the single source for querying structured Runtime data.

Business Rules, Statistics, KPIs, and AI should call the Query Engine rather than implementing separate query mechanisms.

Please verify this decision.

## Content Packages

Content Packages define:

- Objects.
- Relations.
- Events.
- Rules.
- Processes.
- Menus.
- Workspaces.
- Views.
- Forms.
- Reports.
- Statistics.
- KPIs.
- Translations.
- Document Templates.
- Capability Manifest.

Business applications are therefore Content.

The Runtime executes Content.

## GUI Philosophy

GUI is generated by the Runtime.

Packages define:

- Menus.
- Layouts.
- Forms.
- Tables.
- Graphs.
- Process diagrams.
- Dashboards.
- Document layouts.

The Runtime renders native widgets.

No browser runtime is required.

No JavaScript runtime is required.

Everything should adapt to different screen sizes.

Please verify this approach.

## Localization

Localization is a Runtime capability.

Packages contain translations.

Business identifiers remain language-neutral.

The Runtime supports:

- Unicode.
- RTL languages.
- Fallback languages.
- Locale-aware formatting.
- Localized reports.
- Localized document generation.

Please review this architecture.

## Security

Security responsibilities are separated:

- Permissions.
- Capabilities.
- Identity.
- Cryptography.

Packages declare capabilities.

Runtime enforces capabilities on every privileged API call.

Capability declarations are fine-grained.

Packages default to least privilege.

Please verify this model.

## Native Plugins

Native plugins remain isolated processes.

Examples:

- SCADA.
- CAD.
- Office.
- PDF.
- OCR.
- AI.
- Hardware Drivers.

Plugins communicate through versioned RPC contracts.

Plugin failures must never corrupt Runtime state.

Please verify lifecycle requirements.

## AI

AI is external.

AI providers may include:

- OpenAI.
- Claude.
- Gemini.
- Local enterprise AI.
- Future providers.

The Runtime communicates through AI adapters.

AI has no direct database access.

AI receives only authorized structured data.

AI may:

- Query.
- Summarize.
- Explain.
- Compare.
- Recommend.
- Predict.
- Generate drafts.

AI must never:

- Replace deterministic business rules.
- Modify official records directly.
- Approve regulated actions.
- Bypass permissions.

Please verify this philosophy.

## Documents

The source of truth is always structured Runtime data.

Documents are generated representations.

Supported document types include:

- DOCX.
- XLSX.
- PDF.
- CSV.
- ODT.
- ODS.

Office support is modular.

The Runtime should not embed entire office suites.

Please verify this architecture.

## Synchronization

Synchronization remains lightweight.

Core functionality:

- Delta synchronization.
- Offline queues.
- Conflict detection.
- Resumable transfers.
- Selective synchronization.

Peer-assisted synchronization remains optional.

Optional synchronization must compile separately.

Please verify this decision.

## Runtime Size

One of the primary design goals is: "Can it run Open-EQMS?"

The Runtime should remain extremely lightweight.

Target philosophy:

- Small native Runtime.
- Small Content Packages.
- Optional Plugins.
- No embedded browser.
- No embedded office suite.
- No embedded LLM.

Please evaluate whether this architecture can realistically achieve a Runtime footprint in the range of approximately 20-40 MB while preserving maintainability and long-term extensibility.

## Repository

Repository principles include:

- Architecture is the single source of truth.
- ADR-driven development.
- Schemas are first-class artifacts.
- Rule DSL is versioned independently.
- Builder validates everything before signing.
- CI enforces architecture rules.

Please verify whether the repository organization supports long-term maintenance.

## Final Request

Please perform one final comprehensive architecture review.

Do not redesign the platform.

Instead:

- Remove remaining ambiguity.
- Identify hidden complexity.
- Eliminate duplicated concepts.
- Verify consistency.
- Verify long-term maintainability.
- Verify industrial applicability.
- Verify regulatory suitability.
- Verify performance philosophy.
- Verify repository organization.
- Verify Runtime boundaries.

If you believe Architecture Baseline v1.0 is ready for implementation, explicitly state so.

If not, identify only blocking architectural issues.

Ignore implementation details.

Focus exclusively on Architecture Baseline v1.0.

This review is intended to become the final architectural approval before implementation begins.
